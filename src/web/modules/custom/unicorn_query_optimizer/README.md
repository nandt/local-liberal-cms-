# Unicorn Query Optimizer

Τα article listings του dashboard έκαναν 5-15 δευτερόλεπτα (LIBER-4480). Το 93% του
χρόνου ήταν **δύο** queries: το listing και το `COUNT` που τρέχει για τη σελιδοποίηση.

Το module τα ξαναγράφει. Ίδιο URL, ίδιο response, καμία αλλαγή στο frontend.

**Μετρημένο: 9,1s → 0,8s.**

## Τι διορθώνει

### 1. Το `GROUP BY` που δεν χρειάζεται

Το Drupal προσθέτει `GROUP BY base_table.vid, base_table.nid` σε κάθε entity query με
paging, ως άμυνα για διπλές γραμμές από μεταφράσεις. Μαζί του, το `ORDER BY` γίνεται
`ORDER BY max(node_field_data_2.created)` — **aggregate**, που κανένα index δεν μπορεί
να εξυπηρετήσει. Η βάση υλοποιεί και τις 600.000 γραμμές πριν φτάσει στο `LIMIT 25`.

Στα δεδομένα μας **δεν υπάρχει καμία μετάφραση**, οπότε η άμυνα είναι καθαρή σπατάλη.

### 2. Το λάθος index

Η MariaDB διαλέγει `index_merge intersect` πάνω στα `type` και `status`, νομίζοντας ότι
φιλτράρουν. Δεν φιλτράρουν — το 99,98% των εγγραφών περνάει. Καταγεγραμμένο ως
[MDEV-6904](https://jira.mariadb.org/browse/MDEV-6904).

Το `FORCE INDEX` δεν μπορεί να γραφτεί μέσα από το Drupal DB API: το `escapeTable()`
σβήνει παρενθέσεις και κενά. Αντ' αυτού γράφουμε `IF(1, type, NULL)` — ίδια τιμή, αλλά
το index γίνεται μη-χρησιμοποιήσιμο και μένει αυτό του `ORDER BY`.

**Αυτό μπαίνει μόνο μετά από έλεγχο.** Σε στενό φίλτρο θα ήταν καταστροφικό: με
`type='page'` (4 εγγραφές) το query πάει από 0,1ms σε 737ms. Το `EXPLAIN` του ίδιου του
query λέει πόσες γραμμές σκοπεύει να διαβάσει· αν είναι λιγότερο από 5% του πίνακα, δεν
μπαίνει τίποτα.

### 3. Ο tiebreaker

Το `sort=-changed` δεν είναι ντετερμινιστικό: **96% των άρθρων μοιράζονται `changed`**
με κάποιο άλλο, και στην κορυφή υπάρχουν ομάδες 76 και 55 άρθρων με ίδιο timestamp
(κατάλοιπο του migration). Χωρίς δεύτερο κριτήριο, η σελιδοποίηση μπορεί να
διπλοεμφανίσει ή να χάσει άρθρα.

Προστίθεται `nid` **με την ίδια φορά** με το τελευταίο sort. Ανάποδη φορά κοστίζει:
`created ASC, nid DESC` = 109ms, `created ASC, nid ASC` = 0,2ms.

## Πότε ΔΕΝ κάνει τίποτα

Βγαίνει αμέσως, αφήνοντας το query ανέγγιχτο, σε κάθε σχήμα που δεν αναγνωρίζει:

- revision queries (`allRevisions`/`latestRevision`)
- **οποιοδήποτε join σε field table** (`node__field_*`) — εκεί το GROUP BY είναι
  απαραίτητο, χωρίς αυτό τα άρθρα με πολλαπλά tags διπλογράφονται και το
  `fetchAllKeyed()` τα καταρρέει σιωπηλά
- expression που δεν είναι `min()`/`max()` πάνω σε στήλη του sort
- condition σε πίνακα εκτός των γνωστών
- **αν εμφανιστεί έστω μία μετάφραση** στη βάση

## Kill switch

```bash
drush sset unicorn_query_optimizer.enabled 0   # άμεσο off, χωρίς deploy
drush pmu unicorn_query_optimizer -y           # πλήρης απεγκατάσταση
```

Και στις δύο περιπτώσεις τα queries επιστρέφουν στη συμπεριφορά του core.

## 3. Ο index για την ταξινόμηση κατά τίτλο

Ο υπάρχων `node__title_type` είναι **prefix index** — καλύπτει μόνο 191 από τους 255
χαρακτήρες του τίτλου. Ένα prefix index δεν μπορεί να εξυπηρετήσει `ORDER BY`: δύο τίτλοι
που διαφέρουν μετά τον 191ο χαρακτήρα έχουν ίδιο κλειδί, οπότε η σειρά δεν είναι
εγγυημένη. Η MariaDB το αρνείται σωστά, ακόμα και με `FORCE INDEX`.

Το `hook_install` φτιάχνει `unicorn_qo__title_nid (title, nid)` — **πλήρες**. Ταξινόμηση
κατά τίτλο: 250 ms → **0,1 ms**. Ο optimizer το διαλέγει μόνος του.

Κόστος: **+89 MB** σε πίνακα 600.000 άρθρων (264 → 353 MB indexes). Build **0,8 s**.
Το `hook_uninstall` τον σβήνει.

## Μετρήσεις

Πραγματικά HTTP requests στο `/unicornapi/node/article_liberal`, τοπικά, 600.000 άρθρα.

| Ενέργεια στο dashboard | πριν | μετά |
|---|---:|---:|
| **Φόρτωση λίστας** (`sort=-changed`, 25/σελίδα) | **7,4 s** | **0,70 s** |
| Αλλαγή σελίδας (σελίδα 100) | 7,4 s | 0,68 s |
| Ταξινόμηση κατά τίτλο | 9,5 s | **0,61 s** |
| Ταξινόμηση κατά τίτλο, ανάποδα | 9,5 s | 0,79 s |
| Αναζήτηση τίτλου με αποτελέσματα | 7,4 s | **0,25 s** |
| Αναζήτηση τίτλου χωρίς αποτελέσματα | 7,4 s | 0,55 s |
| Φίλτρο ημερομηνίας δημοσίευσης | 9,3 s | 0,66 s |

Ανά query, στο default listing:

| | πριν | μετά |
|---|---:|---:|
| listing | 4951 ms | 0,4 ms |
| COUNT (σελιδοποίηση) | 4145 ms | 62 ms |
| Όλα τα υπόλοιπα (φόρτωση, access, serialize) | 135 ms | 135 ms |

Πιάνει **κάθε** node entity query, όχι μόνο το JSON:API: σκέτο `\Drupal::entityQuery('node')`
από custom controller πάει από **3048 ms σε 0,8 ms**.

## Τι μένει αργό

**Αναζήτηση χωρίς αποτελέσματα: 0,55 s.** Το `LIKE '%όρος%'` σκανάρει όλο τον πίνακα και
δεν μπορεί να σταματήσει νωρίς όταν δεν βρίσκει τίποτα. Με αποτελέσματα είναι 0,25 s,
γιατί σταματάει στα πρώτα 25.

Θα το έλυνε το Solr (`search_api_solr`, ήδη εγκατεστημένο, 610.935 άρθρα indexed) — αλλά
σήμερα δουλεύει μόνο στο production, τα connection settings ζουν στη βάση και όχι στο git,
και αλλάζει το response shape. Δες LIBER-4400/4401.
